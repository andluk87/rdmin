# ТЕХНИЧЕСКОЕ ЗАДАНИЕ
## Разработка системы удалённого доступа и управления компьютерами RemoteAdmin

**Тип продукта:** аналог Radmin Server и Radmin Viewer  
**Версия документа:** 1.0  
**Дата:** 19.10.2026  
**Целевые платформы:** Windows 10/11, Windows Server 2019/2022/2025  
**Тип проекта:** Desktop + Backend + Web Admin Panel  
**Архитектура:** Client–Server, P2P, Relay  
**Статус:** ТЗ для проектирования и разработки

---

# 1. Общее описание проекта

## 1.1. Назначение

Необходимо разработать программный комплекс для удалённого подключения к компьютерам и серверам с возможностью просмотра экрана, управления мышью и клавиатурой, передачи файлов и администрирования устройств через локальную сеть или интернет.

Система должна предоставлять функциональность, сопоставимую с Radmin, но использовать собственную архитектуру, протоколы обмена данными, интерфейс и программную реализацию.

Основной акцент:

- Высокая скорость удалённого управления.
- Минимальная задержка передачи изображения.
- Стабильность соединений.
- Безопасная авторизация.
- Удобный интерфейс.
- Работа в локальных и распределённых сетях.
- Централизованное управление устройствами.
- Возможность масштабирования.
- Поддержка постоянного доступа на явно авторизованных устройствах.

## 1.2. Состав программного комплекса

Разрабатываются четыре основных приложения/сервиса.

**1. RemoteAdmin Server (Agent)**

Устанавливается на удалённый компьютер. Отвечает за захват изображения, обработку команд, управление доступом, передачу файлов и выполнение разрешённых действий.

**2. RemoteAdmin Viewer**

Десктопное приложение оператора, используемое для поиска и организации компьютеров, создания подключений и управления удалёнными устройствами.

**3. RemoteAdmin Backend**

Центральный сервер, обеспечивающий регистрацию устройств, аутентификацию, сигнализацию, управление сессиями, политиками доступа и аудит.

**4. RemoteAdmin Admin Panel**

Веб-интерфейс администратора для управления организациями, пользователями, устройствами, разрешениями и журналами подключений.

## 1.3. Целевая аудитория

- Системные администраторы.
- IT-отделы организаций.
- Специалисты технической поддержки.
- Корпоративные операторы удалённого доступа.
- Владельцы собственных компьютеров и серверов.

## 1.4. Поддерживаемые ОС

Для первого релиза:

- Windows 10 x64 (поддерживаемые редакции в согласованной тестовой матрице).
- Windows 11 x64.
- Windows Server 2019 x64.
- Windows Server 2022 x64.
- Windows Server 2025 x64.

Linux, macOS, Android и iOS не входят в первую версию.

Поддержка устаревших операционных систем Windows не требуется.

# 2. Основные пользовательские сценарии

## Сценарий №1. Управление компьютером в локальной сети

1. Пользователь устанавливает Server на удалённый компьютер.
2. Настраивает разрешённый способ подключения.
3. Оператор запускает Viewer.
4. Добавляет устройство по IP-адресу, DNS-имени или идентификатору.
5. Выбирает «Подключиться».
6. Проходит аутентификацию и процедуру подтверждения доступа.
7. Получает изображение удалённого рабочего стола.
8. Управляет мышью и клавиатурой в пределах разрешений.
9. Завершает сеанс.

## Сценарий №2. Подключение через интернет

1. Server устанавливает исходящее защищённое соединение с Backend.
2. Backend обновляет статус устройства.
3. Viewer запрашивает подключение.
4. Backend проверяет полномочия оператора.
5. Server применяет локальные политики и при необходимости запрашивает согласие пользователя.
6. Система согласовывает прямое P2P-соединение.
7. Если P2P недоступно, используется Relay.
8. После успешной аутентификации начинается удалённая сессия.

## Сценарий №3. Постоянный административный доступ

1. Локальный администратор устройства включает режим unattended access.
2. Указывает разрешённых пользователей или группы.
3. Настраивает права и ограничения.
4. Подтверждает включение режима.
5. Server сохраняет политику защищённым способом.
6. В дальнейшем авторизованный оператор может подключаться без разового подтверждения, если это допускает политика.
7. Все подключения регистрируются, а текущий сеанс отображается пользователю при наличии интерактивного рабочего стола.

Режим не должен активироваться скрытно или без соответствующих полномочий.

## Сценарий №4. Передача файлов

1. Оператор открывает разрешённую удалённую сессию.
2. Выбирает «Передача файлов».
3. Открывается двухпанельный файловый менеджер.
4. Выбирает локальные и удалённые файлы.
5. Запускает копирование.
6. Отслеживает прогресс.
7. При обрыве соединения может продолжить передачу.

## Сценарий №5. Подключение для технической поддержки

1. Пользователь запускает Server или уже установленный Agent.
2. Сообщает оператору одноразовый код подключения.
3. Оператор вводит код в Viewer.
4. Пользователь видит запрос с именем оператора и требуемыми правами.
5. Подтверждает или отклоняет доступ.
6. В ходе работы может отключить управление или завершить сессию.

# 4. Архитектура системы

## 4.1. Общая схема взаимодействия

Основные компоненты:

**Viewer → Backend → Server Agent**

Backend используется для идентификации, проверки прав, обнаружения устройств и согласования соединений.

После согласования создаётся канал:

**Viewer ↔ Server Agent (P2P)**

Если прямое соединение невозможно:

**Viewer ↔ Relay ↔ Server Agent**

Видео и управляющие команды не должны проходить через прикладной Backend при штатной работе P2P.

Relay осуществляет транспортную передачу зашифрованных данных, не получая доступа к содержимому сеанса.

## 4.2. Сервисы Backend

Backend логически разделяется на:

1. API Service — обработка HTTP-запросов.
2. Auth Service — аутентификация и проверка полномочий.
3. Device Registry — реестр устройств.
4. Session Manager — управление удалёнными сессиями.
5. Signaling Gateway — обмен служебными сообщениями для установления соединений.
6. Policy Service — централизованные политики.
7. Audit Service — аудит действий.
8. Notification Service — уведомления.
9. STUN/TURN Infrastructure — обеспечение транспортной связности.
10. Admin Web Application — административный интерфейс.

Для MVP допускается модульный монолит с логическим разделением сервисов и единым развёртыванием Backend.

Разработка отдельных микросервисов на первом этапе необязательна.

# 5. Технические требования к RemoteAdmin Server

## 5.1. Установка и системная служба

**S-001.** Server должен поставляться в виде подписанного MSI-установщика.

**S-002.** Установка должна выполняться с повышенными правами администратора Windows.

**S-003.** После установки должна регистрироваться Windows Service.

**S-004.** Имя службы: `RemoteAdminAgent` (рабочее).

**S-005.** Служба должна поддерживать автоматический запуск после перезагрузки, если пользователь или администратор явно включил соответствующий режим.

**S-006.** Служба должна корректно запускаться без открытого GUI.

**S-007.** Для взаимодействия с текущим рабочим столом должен применяться отдельный процесс User Session Worker.

**S-008.** В пользовательской сессии должна присутствовать видимая утилита управления агентом: состояние, активные подключения, разрешения, отключение доступа.

**S-009.** Межпроцессное взаимодействие Windows Service ↔ Session Worker реализуется через защищённый IPC с ACL и проверкой вызывающей стороны.

**S-010.** Агент должен корректно завершаться и освобождать системные ресурсы при остановке службы.

**S-011.** Деинсталлятор должен удалять службы, исполняемые файлы и установленные компоненты, оставляя пользовательские настройки только по явно выбранной политике.

## 5.2. Регистрация устройства

При первом запуске Agent должен:

- Сгенерировать уникальный UUID устройства.
- Создать асимметричную пару ключей устройства.
- Сохранить закрытый ключ в защищённом хранилище Windows.
- Определить версию Windows и архитектуру.
- Определить версию агента.
- Получить основные параметры системы.
- Предоставить пользователю процедуру привязки к организации.
- Выполнить проверку регистрации через Backend.

Пример данных устройства:

| Поле | Тип | Назначение |
|---|---|---|
| device_id | UUID | Постоянный ID |
| display_name | string | Имя компьютера |
| hostname | string | Имя Windows |
| os_name | string | ОС |
| os_version | string | Версия ОС |
| agent_version | string | Версия агента |
| public_key | string | Публичный ключ |
| organization_id | UUID | Организация |
| last_seen_at | datetime | Последняя активность |
| status | enum | Online/Offline/Blocked |

Приватный ключ устройства никогда не отправляется на Backend.

## 5.3. Состояния агента

Предусмотреть состояния:

- `UNREGISTERED` — не привязан к организации.
- `OFFLINE` — не подключён к Backend.
- `ONLINE` — доступен.
- `CONNECTING` — устанавливается сессия.
- `WAITING_APPROVAL` — ожидается согласие.
- `BUSY` — идёт сеанс управления.
- `RECONNECTING` — восстановление соединения.
- `DISABLED` — доступ отключён.
- `ERROR` — ошибка агента.

При сбое связи с Backend Agent должен выполнять повторное подключение с экспоненциальной задержкой и ограничением частоты запросов.

## 5.4. Захват изображения рабочего стола

**S-020.** Захват изображения реализовать с использованием DXGI Desktop Duplication API.

**S-021.** Предусмотреть использование Windows.Graphics.Capture там, где это применимо и разрешено настройками Windows.

**S-022.** Минимально поддерживаемые разрешения: 1280×720 и 1920×1080.

**S-023.** Поддержка 2560×1440 и 3840×2160 — при наличии достаточных ресурсов; для MVP производительность на этих разрешениях не гарантируется.

**S-024.** Частота обновления изображения должна адаптироваться к производительности компьютера и качеству сети.

Режимы:

- Экономичный — до 10 FPS.
- Стандартный — до 30 FPS.
- Высокий — до 60 FPS, при наличии технической возможности.

**S-025.** Поддержать аппаратное кодирование H.264, при отсутствии доступного энкодера — программный fallback.

**S-026.** Разрешение и битрейт должны автоматически адаптироваться к условиям сети.

**S-027.** Необходимо корректно обрабатывать смену разрешения экрана, подключение/отключение монитора и изменение DPI.

**S-028.** Передавать положение и форму курсора отдельно там, где это позволяет уменьшить задержку.

**S-029.** Поддерживать захват отдельных мониторов.

**S-030.** Поддерживать портретную ориентацию монитора.

При блокировке Windows, переключении на защищённый рабочий стол или при отображении UAC должны соблюдаться ограничения и механизмы безопасности ОС. Если изображение недоступно, Viewer должен показывать соответствующее состояние, а не пытаться обходить системную защиту.

## 5.5. Управление мышью

Необходимо реализовать:

- Перемещение курсора.
- Одинарный клик.
- Двойной клик.
- Правую и среднюю кнопки мыши.
- Прокрутку колеса.
- Горизонтальную прокрутку при поддержке устройства.
- Drag and Drop внутри удалённого рабочего стола.
- Точное преобразование координат при масштабировании.
- Корректную обработку нескольких мониторов.

Координаты управления должны передаваться в нормализованном формате с идентификатором дисплея или актуальной геометрией виртуального рабочего стола.

Управляющие события должны приниматься только от авторизованной сессии с правом `REMOTE_CONTROL`.

## 5.6. Управление клавиатурой

Необходимо поддержать:

- Ввод символов.
- Русскую и английскую раскладку.
- Shift, Ctrl, Alt, Win.
- Горячие клавиши.
- Функциональные клавиши F1–F12.
- Комбинации с несколькими модификаторами.
- Корректный отпуск клавиш при потере связи.
- Передачу Unicode-текста допустимым способом.

Viewer должен различать локальные горячие клавиши приложения и команды, предназначенные удалённой машине.

Системные комбинации, связанные с безопасностью Windows, могут выполняться только поддерживаемыми Windows механизмами и при наличии полномочий. Обход защиты ОС не допускается.

## 5.7. Режимы доступа

### Full Control

Разрешает просмотр экрана и управление мышью/клавиатурой.

### View Only

Разрешает только просмотр изображения. События управления не должны отправляться или исполняться.

### File Transfer

Разрешает файловые операции в рамках отдельного права.

### Chat

Позволяет обмениваться сообщениями.

Права должны проверяться Agent для каждого типа действия, независимо от состояния элементов управления в Viewer.

## 5.8. Управление сеансами

Каждому сеансу назначается UUID.

Server должен хранить:

- ID текущей сессии.
- ID оператора.
- ID Viewer.
- Время начала.
- Текущий статус.
- Разрешённые функции.
- Состояние транспортного соединения.

Необходимо предусмотреть:

- Завершение сессии по команде оператора.
- Прекращение сессии локальным пользователем.
- Прерывание при отзыве разрешений.
- Прерывание по политике безопасности.
- Автоматическое освобождение ресурсов.
- Повторное подключение после кратковременного обрыва.
- Ограничение одновременных управляющих сессий.

В MVP разрешается одна активная управляющая сессия на один интерактивный рабочий стол.

Новый оператор должен получать сообщение «Устройство занято» либо запрос на передачу управления, если такая функция будет включена в политику.

## 5.9. Передача файлов

Реализовать файловый API Agent.

Основные операции:

- Просмотр разрешённых каталогов.
- Получение списка файлов.
- Создание папок.
- Загрузка файлов.
- Скачивание файлов.
- Переименование.
- Удаление после подтверждения.
- Получение размера и атрибутов.
- Отмена операции.

Функциональные требования:

- Передача в чанках по 4 MiB по умолчанию.
- Контроль целостности SHA-256.
- Докачка после разрыва.
- Передача файлов размером до 2 GiB в MVP.
- Отображение скорости.
- Отображение оставшегося объёма данных.
- Отмена и повтор операции.
- Проверка допустимости целевого пути.
- Предотвращение path traversal.
- Соблюдение Windows ACL и ограничений разрешённых директорий.

Файловые операции не должны автоматически получать расширенные права только потому, что служба Agent запущена с повышенными привилегиями.

## 5.10. Буфер обмена

Для MVP необходима синхронизация текста:

- Viewer → Server.
- Server → Viewer.

Параметры:

- Unicode.
- Максимальный размер текстовой передачи: 1 MiB.
- Возможность отключить синхронизацию.
- Запрет в режиме View Only, если не выдано отдельное разрешение.
- Исключение бесконечных циклов синхронизации.

Передача файлов через буфер обмена — отдельная функция последующего релиза.

## 5.11. Локальная конфигурация Agent

Необходимо предусмотреть интерфейс настроек:

- Состояние службы.
- ID устройства.
- Имя компьютера.
- Привязанная организация.
- Состояние соединения.
- Разрешённые способы доступа.
- Постоянный доступ.
- Подтверждение подключений.
- Настройки сети.
- Журнал подключений.
- Проверка обновлений.
- Отключение удалённого доступа.

Изменение критических настроек требует соответствующих локальных административных прав.

# 7. Backend — серверная часть

## 7.1. Назначение Backend

Backend отвечает за:

- Учётные записи.
- Организации.
- Устройства.
- Политики доступа.
- Сессии.
- Сигнализацию.
- Историю операций.
- Авторизацию Viewer и Agent.
- Управление Relay-инфраструктурой.
- Административный интерфейс.

Backend не должен выполнять захват рабочего стола или обработку пользовательского ввода.

## 7.2. Auth Module

Функции:

- OIDC-авторизация пользователей.
- Проверка JWT access token.
- Обновление токенов через безопасный OIDC-flow.
- MFA с использованием возможностей Identity Provider.
- Управление ролями.
- Отзыв сессий.
- Проверка привязки пользователя к организации.
- Проверка привязки Viewer к доверенному устройству.

Для Viewer использовать Authorization Code Flow с PKCE и системным браузером.

Refresh token при необходимости хранить через Windows Credential Manager или DPAPI.

Backend должен проверять подпись и обязательные claims токенов.

## 7.3. Device Registry

Функции:

- Регистрация устройства.
- Привязка к организации.
- Подтверждение регистрации.
- Обновление информации.
- Получение состояния.
- Отзыв доступа.
- Блокировка устройства.
- Удаление устройства.
- Поиск.
- Фильтрация.
- Группировка.

Каждый зарегистрированный агент должен иметь собственную криптографическую идентичность.

Регистрация выполняется через одноразовый enrollment token или иной согласованный защищённый механизм.

## 7.4. Session Manager

Session Manager управляет жизненным циклом подключения.

Статусы:

- `REQUESTED`
- `PENDING_APPROVAL`
- `NEGOTIATING`
- `ACTIVE`
- `RECONNECTING`
- `REJECTED`
- `EXPIRED`
- `FAILED`
- `CLOSED`

Основные функции:

- Проверка прав.
- Создание сессии.
- Отправка запроса Agent.
- Получение подтверждения.
- Согласование соединения.
- Контроль жизненного цикла.
- Завершение сессии.
- Запись метаданных в журнал.
- Реакция на отзыв доступа.

При создании сессии должны фиксироваться разрешения именно на данный сеанс.

Обновление прав в дальнейшем должно приводить к повторной проверке или прекращению доступа.

## 7.5. Signaling Gateway

Основной транспорт: WebSocket поверх TLS.

Backend должен обеспечивать обмен:

- `session.request`
- `session.approve`
- `session.reject`
- `session.offer`
- `session.answer`
- `session.ice_candidate`
- `session.connected`
- `session.disconnected`
- `session.terminate`
- `device.status`
- `policy.updated`

Все сообщения должны иметь:

- Версию протокола.
- ID сообщения.
- Тип.
- Время.
- ID отправителя.
- ID получателя.
- Payload.
- ID сессии, если применимо.

Должны быть предусмотрены ограничения размеров сообщений, контроль полномочий, защита от повторной обработки и дедупликация.

## 7.6. Connection Broker

Требования:

1. Проверять право создания подключения.
2. Выбирать допустимые способы транспорта.
3. Выдавать краткоживущие credentials для TURN.
4. Обеспечивать получение ICE candidates.
5. Отслеживать результат установления связи.
6. Предоставлять Viewer диагностический результат.

При доступности P2P предпочтение отдавать прямому соединению.

При невозможности прямого соединения использовать Relay.

Система должна поддерживать IPv4 и IPv6, если они доступны.

## 7.7. Relay Infrastructure

Для MVP использовать coturn.

Требования:

- TURN over UDP.
- TURN over TCP.
- TURN over TLS.
- Поддержка временных credentials.
- Ограничения по пользователям и сессиям.
- Метрики загрузки.
- Контроль сетевого трафика.
- Защита от злоупотребления Relay.

Рекомендуется использовать UDP 3478 и TLS 5349; при необходимости предусмотреть альтернативный TLS endpoint на 443.

Фактический набор открытых портов определяется инфраструктурой развёртывания.

При корпоративных ограничениях сети и невозможности использования UDP система должна применять разрешённый fallback, если доступна подходящая транспортная конфигурация.

## 7.8. Policy Service

Политики:

- Разрешение Full Control.
- Разрешение View Only.
- Передача файлов.
- Буфер обмена.
- Чат.
- Постоянный доступ.
- Подтверждение пользователем.
- Ограничение длительности сеанса.
- Список разрешённых операторов.
- Список разрешённых групп.
- Сетевые ограничения.
- Ограничение одновременных сессий.
- Разрешённые каталоги для передачи файлов.

Политики наследуются от организации или группы устройств.

Локально заданные запреты не могут быть автоматически сняты обычным оператором.

## 7.9. Audit Service

События, подлежащие регистрации:

- Успешная авторизация.
- Ошибка авторизации.
- Регистрация устройства.
- Изменение владельца.
- Изменение прав.
- Запрос подключения.
- Подтверждение подключения.
- Отклонение подключения.
- Начало сеанса.
- Завершение сеанса.
- Отключение пользователем.
- Файловая операция: тип, путь в пределах политики журналирования, размер и результат.
- Изменение политик.
- Блокировка устройства.

Каждое событие должно содержать:

- Event ID.
- Timestamp UTC.
- Organization ID.
- Actor ID.
- Device ID.
- Session ID.
- Event Type.
- Outcome.
- IP, если обработка соответствует политике приватности.
- Дополнительные безопасные метаданные.

Содержимое экрана, вводимые клавиши, тексты документов и пароли не должны записываться в технические логи.

## 7.10. Notifications

Система должна поддерживать уведомления:

- Запрос подключения.
- Новая сессия.
- Отключение.
- Ошибка доступа.
- Изменение прав.
- Обновление доступно.
- Устройство отключилось.

В MVP достаточно уведомлений в Viewer, Agent UI и Admin Panel.

Email и внешние уведомления допускается добавить позднее.

# 8. Backend API

## 8.1. Общие правила API

Базовый URL:

`https://api.example.com/api/v1`

Формат: JSON.

Аутентификация: Bearer Token.

Версионирование: `/api/v1`.

Для всех запросов:

- Проверять схему данных.
- Ограничивать размер payload.
- Проверять права.
- Возвращать корректные HTTP-коды.
- Использовать UUID для основных идентификаторов.
- Поддерживать пагинацию.
- Предусмотреть idempotency key для критичных операций создания.

Формат ошибки:

`{ code, message, request_id, details }`

Поле `details` не должно раскрывать внутренние секреты или конфигурацию.

## 8.2. API пользователей

| Метод | Endpoint | Назначение |
|---|---|---|
| GET | /users/me | Текущий пользователь |
| GET | /users | Список пользователей |
| GET | /users/{id} | Информация |
| PATCH | /users/{id} | Изменение данных |
| POST | /users/{id}/roles | Назначение роли |
| DELETE | /users/{id}/roles/{role} | Отзыв роли |

Удаление и редактирование пользователей должны проверяться в контексте организации.

## 8.3. API устройств

| Метод | Endpoint | Назначение |
|---|---|---|
| POST | /enrollment-tokens | Создать токен регистрации |
| POST | /devices/enroll | Зарегистрировать Agent |
| GET | /devices | Список устройств |
| GET | /devices/{id} | Получить устройство |
| PATCH | /devices/{id} | Изменить данные |
| DELETE | /devices/{id} | Удалить регистрацию |
| POST | /devices/{id}/disable | Заблокировать доступ |
| POST | /devices/{id}/enable | Разблокировать |
| GET | /devices/{id}/status | Текущий статус |
| GET | /devices/{id}/policy | Получить политику |
| PUT | /devices/{id}/policy | Изменить политику |

Пример ответа `GET /devices/{id}`:

## 8.4. API удалённых сессий

| Метод | Endpoint | Назначение |
|---|---|---|
| POST | /sessions | Создать запрос |
| GET | /sessions/{id} | Получить состояние |
| POST | /sessions/{id}/approve | Подтвердить |
| POST | /sessions/{id}/reject | Отклонить |
| POST | /sessions/{id}/terminate | Завершить |
| GET | /sessions | История |
| GET | /sessions/{id}/events | События |

Пример тела запроса `POST /sessions`:

`{ device_id, requested_permissions, connection_preference, viewer_device_id }`

Поля:

- `device_id` — UUID.
- `requested_permissions` — массив разрешений.
- `connection_preference` — auto/direct/relay.
- `viewer_device_id` — ID клиента оператора.

Пример ответа:

`{ session_id, status, expires_at, signaling_channel }`

Создание сессии не означает, что доступ автоматически разрешён.

# 10. Сетевой протокол и передача данных

## 10.1. Общий принцип

Предлагается использовать WebRTC как транспортную основу медиа и интерактивных данных.

Преимущества:

- Поддержка ICE.
- Поддержка STUN/TURN.
- Передача видеопотока.
- Контроль качества канала.
- DataChannel для произвольных сообщений.
- Защищённый транспорт.

Необходимо использовать стандартные криптографические механизмы WebRTC, не разрабатывать собственные алгоритмы шифрования.

## 10.2. Каналы связи

В одной сессии логически выделяются:

**Video Channel**

- Захваченное изображение.
- H.264.
- Адаптивный битрейт.
- Контроль частоты кадров.

**Control Channel**

- Начало сессии.
- Изменение прав.
- Выбор монитора.
- Изменение качества.
- Завершение соединения.

**Input Channel**

- Клавиатура.
- Мышь.
- Скроллинг.
- Системные события ввода.

**Clipboard Channel**

- Текстовые данные.
- Синхронизация.

**File Transfer Channel**

- Метаданные файлов.
- Бинарные блоки.
- Контроль целостности.
- Подтверждения.

**Chat Channel**

- Сообщения пользователя и оператора.

Логические каналы могут реализовываться отдельными WebRTC DataChannel.

Для критичных управляющих операций использовать надёжную упорядоченную доставку; для частых координат курсора допустим канал с ограниченными ретрансляциями. События нажатия/отпускания клавиш должны передаваться надёжно и восстанавливаться безопасно после сбоя.

## 10.3. Последовательность установления соединения

1. Viewer проходит аутентификацию.
2. Viewer отправляет запрос на сессию.
3. Backend проверяет права.
4. Backend уведомляет Agent.
5. Agent проверяет локальную политику.
6. Если требуется, отображает запрос пользователю.
7. Agent подтверждает или отклоняет сессию.
8. Viewer и Agent обмениваются SDP и ICE candidates.
9. Проверяется криптографическая идентичность сторон и привязка DTLS fingerprint к сеансу.
10. Устанавливается P2P-канал либо Relay.
11. Agent начинает передачу разрешённых данных.
12. Viewer переходит в состояние ACTIVE.

Подписанные подтверждения идентичности сторон должны защищать соединение от подмены при компрометации или ошибке сигнального канала.

## 10.4. Контроль соединения

Рекомендуемые значения по умолчанию:

- Heartbeat Agent → Backend: каждые 15 секунд.
- Признание устройства Offline: после 45 секунд без heartbeat.
- Срок ожидания подтверждения подключения: 60 секунд.
- Попытка восстановления интерактивной сессии: до 30 секунд.
- Срок жизни одноразового кода подключения: 5 минут.
- Срок действия credentials TURN: ограниченный временем установления и жизни сеанса.

Все значения должны быть вынесены в конфигурацию и корректно обрабатываться при изменении.

## 10.5. Безопасность протокола

Требования:

- TLS 1.3 для HTTPS/WSS при поддержке клиентов и инфраструктуры.
- Шифрование медиаданных и DataChannel средствами WebRTC.
- Проверка сертификатов и идентичности узлов.
- Подпись или криптографическая привязка согласуемых параметров соединения к идентичности сторон.
- Сессионные разрешения с коротким сроком действия.
- Защита от повторного использования приглашений.
- Запрет неавторизованной отправки управляющих команд.
- Ограничение размера сообщений.
- Защита от переполнения очередей.

TURN/Relay не должен обладать возможностью расшифровки содержимого удалённого рабочего стола.

# 11. Права пользователей и безопасность

## 11.1. Ролевая модель

Предусмотреть роли:

**Organization Admin**

Управление организацией, пользователями, устройствами и политиками.

**Device Admin**

Управление назначенными устройствами и настройками доступа.

**Operator**

Подключение к разрешённым устройствам.

**Viewer Only**

Просмотр устройств без права управления.

**Auditor**

Просмотр разрешённых журналов.

Отдельно существует локальный пользователь целевого компьютера, который может подтверждать или прекращать интерактивную сессию.

## 11.2. Матрица разрешений

| Действие | Admin | Operator | Viewer Only | Auditor |
|---|---|---|---|---|
| Список разрешённых устройств | Да | Да | Да | По политике |
| Просмотр экрана | По политике | По политике | По политике | Нет |
| Управление мышью | По политике | По политике | Нет | Нет |
| Передача файлов | По политике | По политике | Нет | Нет |
| Изменение политик | Да | Нет | Нет | Нет |
| Управление пользователями | Да | Нет | Нет | Нет |
| Просмотр аудита | Да | Свои события | Нет | Да |

При этом роль сама по себе не даёт автоматического права подключения к любому устройству. Обязательна дополнительная проверка разрешений конкретного устройства.

## 11.3. Защита постоянного доступа

Режим unattended access должен:

- Включаться только уполномоченным локальным администратором.
- Требовать явной настройки.
- Ограничиваться конкретными пользователями или группами.
- Проверять дополнительные требования MFA по политике.
- Регистрировать подключения.
- Позволять отключать режим.
- Не маскировать работу агента.
- Уведомлять локального пользователя об активных или недавно завершённых сеансах при наличии пользовательской сессии.

## 11.4. Принцип минимальных привилегий

Основные правила:

- GUI Viewer не требует административных прав для обычной работы.
- Agent разделён на привилегированный служебный компонент и пользовательские процессы.
- Действия выполняются с минимально необходимыми полномочиями.
- Файловый менеджер соблюдает разрешённые пути и ACL.
- Доступ к защищённым функциям ОС осуществляется только через предусмотренные механизмы.
- Нельзя обходить UAC, антивирусные механизмы или системные политики Windows.

## 11.5. Защита данных

- Закрытые ключи устройств должны защищаться средствами ОС.
- Пароли и токены не записываются в обычные логи.
- Нельзя передавать credentials через незашифрованные каналы.
- Необходимо поддержать отзыв устройства и его ключей.
- Конфигурация политик должна иметь контроль целостности.
- Все устанавливаемые обновления должны проверяться по цифровой подписи.
- Телеметрия не должна содержать видеокадры, документы и содержимое пользовательского ввода.

# 13. Нефункциональные требования

## 13.1. Производительность

Целевые показатели для MVP при подходящем тестовом оборудовании и сети:

| Показатель | Цель |
|---|---|

Показатели задержки и нагрузки должны подтверждаться в согласованной тестовой лаборатории.

На скорость соединения существенно влияют видеокарта, аппаратный энкодер, качество сети и тип транспорта.

## 13.2. Требования к масштабированию

Первоначальная целевая нагрузка Backend:

- 1 000 зарегистрированных активных Agent.
- 100 одновременных удалённых сессий.
- 100 одновременных операторов.
- 10 000 событий аудита в сутки.

Приведённые показатели являются исходными требованиями для нагрузочных испытаний, а не автоматически гарантируемой пропускной способностью выбранного сервера.

Relay должен рассчитываться отдельно с учётом среднего видеобитрейта, двунаправленного трафика и пропускной способности сети.

## 13.3. Надёжность

Необходимо:

- Корректно обрабатывать закрытие Viewer.
- Не допускать зависания Agent после обрыва соединения.
- Автоматически освобождать ресурсы завершённой сессии.
- Защищать базу данных от повреждения при неудачных транзакциях.
- Использовать health checks.
- Предусмотреть резервное копирование PostgreSQL.
- Обеспечить возможность восстановления после сбоя Backend.
- Реализовать безопасный откат обновления Agent.

## 13.4. Логирование

Уровни:

- ERROR.
- WARN.
- INFO.
- DEBUG.

Каждое событие должно иметь timestamp, component, request/session ID и диагностическую категорию.

Чувствительные поля должны маскироваться.

Срок хранения аудита по умолчанию — 90 дней, с возможностью изменения согласно политике организации и применимым требованиям.

## 13.5. Обновления

- Все пакеты должны иметь цифровую подпись.
- Viewer проверяет наличие обновлений.
- Agent поддерживает безопасную процедуру обновления.
- Обновление не должно самовольно прерывать активный сеанс.
- После неуспешного обновления предусмотрен rollback.
- Обновления должны поддерживать staged rollout.

Автоматическое обновление Agent допускается только в рамках явно заданной политики.

- Проверка неподписанного обновления.

# 20. Основные технические риски

**Риск 1. Работа с защищёнными рабочими столами Windows**

DXGI-захват имеет системные ограничения при переключении desktop и UAC. Необходимо отдельно определить и протестировать поддерживаемые сценарии работы с экраном входа и повышенными привилегиями.

**Риск 2. Задержки передачи изображения**

Необходимо тестировать разные GPU, программное кодирование, битрейт и сетевые сценарии.

**Риск 3. Корпоративные сети**

Некоторые NAT, firewall и proxy могут препятствовать P2P. Нужны корректный TURN fallback и диагностика.

**Риск 4. Работа с несколькими мониторами**

Требуется правильная обработка геометрии, координат, DPI и переключения видеопотока.

**Риск 5. Конкурентный доступ**

Должна быть исключена ситуация, когда несколько операторов одновременно управляют одним рабочим столом без предусмотренного согласования.

**Риск 6. Безопасность Agent**

Компрометация удалённого агента является высококритичным риском. Обязательны минимальные привилегии, проверка IPC, защита ключей и безопасные обновления.

**Риск 7. Совместимость антивирусных продуктов**

Необходимо использовать подписанные исполняемые файлы, документировать поведение и устранять причины возможных ложных срабатываний. Обход или отключение защитного ПО не предусматриваются.
